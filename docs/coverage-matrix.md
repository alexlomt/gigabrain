# Surface coverage matrix

Gigabrain exposes its memory engine through three surfaces:

- **MCP** — the `gigabrain_*` tools registered for Codex / Claude / Hermes
  (`lib/core/codex-mcp.js`).
- **CLI** — the `gigabrainctl` verbs (`scripts/gigabrainctl.js`).
- **HTTP** — the local `/gb/*` JSON API used by the web console and the
  Spark↔Gigabrain bridge (`lib/core/http-routes.js`).

The matrix below maps each capability to the surface(s) that expose it. It is a
deliberate, asymmetric design: write/agent-loop capabilities live on MCP, operator
maintenance lives on the CLI, and read/inspection surfaces are mirrored to HTTP for
the console. A blank cell is an intentional non-goal, not an oversight — the
rationale is in the notes.

Legend: ✅ first-class · 🟡 partial / indirect · ⬜ not exposed (by design or
planned).

| Capability | MCP | CLI | HTTP | Notes |
| --- | :---: | :---: | :---: | --- |
| **capture** | ✅ `gigabrain_remember` | 🟡 `sync-hosts`, `import-openclaw` | 🟡 `POST /gb/suggestions` | MCP is the live remember-intent write path. The CLI captures *indirectly* by syncing host memory files and importing legacy registries (it has no raw `capture` verb). HTTP capture is the bridge ingest of structured Spark suggestions, not free-form writes. |
| **recall** | ✅ `gigabrain_recall` | ✅ `orchestrator explain` | ✅ `POST /gb/recall`, `POST /gb/recall/explain` | All three surfaces read. The CLI `orchestrator explain` is the recall-explain path; HTTP `/gb/recall` uses POST for the request body but performs no write. |
| **checkpoint** | ✅ `gigabrain_checkpoint` | ⬜ | ⬜ | Episodic session-log checkpoints are an agent-loop concern, so they live only on MCP. Operators do not checkpoint from the CLI, and the console does not write checkpoints. |
| **adjudications** | ✅ `gigabrain_adjudications` | ✅ `review adjudications` | ✅ `GET /gb/adjudications` | Read the arbitration ledger (who won / why) on every surface. |
| **beliefs-as-of** | ✅ `gigabrain_beliefs_as_of` | ✅ `review beliefs-as-of --at <iso>` | ✅ `GET /gb/beliefs-as-of?at=<iso>` | Bitemporal "what did we believe at time T" query, mirrored across all three. |
| **review-queue** | ✅ `gigabrain_review_queue` | ✅ `review queue` | ✅ `GET /gb/review-queue` | Filter the human-review queue by status / reason code on every surface. |
| **watch** | ⬜ | ✅ `watch` (`watch --install-hook`) | ⬜ | The filesystem/host watcher and its hook installer are an operator/runtime concern, exposed only on the CLI. |
| **handoff** | 🟡 `gigabrain_export_brief` | ✅ `handoff` (alias: `passport`, deprecated) | ⬜ | The full Memory Audit + Handoff Record (report + `handoff-records/`) is generated by the CLI `handoff` verb. MCP exposes the narrower per-host safe Memory Brief (`gigabrain_export_brief`). The console does not generate the report over HTTP. |
| **legacy-drop** | ⬜ | ✅ `migrate legacy-drop` | ⬜ | The guarded drop of the deprecated `memories` dual-write table (containment check + snapshot + ledger event) is wired as the CLI `migrate legacy-drop` verb (U18) — `--dry-run` reports containment only; the real run is containment-gated and refuses to drop while orphan legacy rows exist. An operator-only lifecycle verb, so it is not exposed on MCP or HTTP. |
| **vault** | 🟡 (via `recall`) | ✅ `vault sync`, `vault status` | 🟡 (via `recall`) | READ-ONLY Obsidian reference corpora (`config.native.vaults[]`). Vault chunks are surfaced through the **unified recall surface** (so MCP `gigabrain_recall` and HTTP `POST /gb/recall` reach them indirectly — neutral, labeled, **zero arbitration participation**: a vault chunk NEVER becomes a belief and never enters adjudication). The dedicated operator verbs live only on the CLI: `vault sync` (re-ingest configured vaults; budgeted) and `vault status` (per-vault chunk counts + last sync + skipped-evicted). With `vaults:[]` (default) every path is a graceful no-op. |

## Read across, write narrowly

Two patterns explain the shape of the matrix:

1. **Inspection capabilities are mirrored.** `adjudications`, `beliefs-as-of`, and
   `review-queue` are read everywhere — agents inspect them via MCP, operators via
   the CLI, and the console via HTTP. These are the trust-control-plane surfaces and
   benefit from being uniformly reachable.

2. **Writes and lifecycle stay on their owner surface.** `checkpoint` (agent loop)
   is MCP-only; `watch` and `legacy-drop` (runtime/operator lifecycle) are CLI-only;
   raw `capture` is an MCP write while the CLI only *imports* and HTTP only *ingests
   structured suggestions*. This keeps the blast radius of each mutating path
   aligned with the actor that owns it.

When you add a new capability, record its row here in the same PR so the asymmetry
stays a deliberate, documented choice rather than drift.
